# Pesquisa do ponto 3: proteção da `main` em GitHub ou GitLab Free

**Consultada em:** 2026-09-24  
**Escopo:** comparar proteção de branch privada no GitHub, incluindo a proposta de transferir o repositório para a conta pessoal GitHub Pro do irmão, com a opção GitLab Free. Pesquisa sem alteração de configurações/remotes. O repositório reporta `main` com `protected=false`. O usuário esclareceu que Polaris ainda não está publicado nem conectado à Vercel; os projetos poderão ser configurados depois da fundação.

## Conclusão

Há duas rotas viáveis:

- **Menor mudança:** habilitar branch protection/ruleset no GitHub. A documentação atual exige GitHub Pro, Team ou Enterprise para branches protegidas em repositórios privados; GitHub Free só inclui o recurso em repositórios públicos. O erro observado pela API é compatível com esse limite, mas confirmar o plano da conta antes de decidir. ([GitHub: managing protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches), [GitHub REST API](https://docs.github.com/en/rest/branches/branch-protection))
- **Sem pagar GitHub Pro, com custo de migração:** GitLab Free oferece branches protegidas, merge requests e pipelines bloqueantes, inclusive para projetos privados. Vercel lista GitLab Free como provedor Git e gera Preview Deployments para merge requests. A troca exige migrar o remoto e reconfigurar CI/secrets/integração, não apenas mudar uma opção de branch. ([GitLab: branch rules](https://docs.gitlab.com/user/project/repository/branches/branch_rules/), [GitLab: pipelines must succeed](https://docs.gitlab.com/user/project/merge_requests/auto_merge/), [Vercel: GitLab](https://vercel.com/docs/git/vercel-for-gitlab))

- **Transferir para o GitHub Pro pessoal do irmão:** tecnicamente resolve o bloqueio de plano para proteger uma branch privada, desde que a conta Pro permaneça ativa e o proprietário configure a regra. Em transferência entre contas pessoais, GitHub mantém Git, Issues, PRs, secrets e webhooks, adiciona o proprietário anterior como colaborador e deixa o novo titular como owner único. O usuário mantém write/PR/merge, mas não as ações administrativas de owner, incluindo manter plano e configurações. Como o app ainda não está conectado à Vercel, a troca não interrompe deployment atual; mais tarde, a conta proprietária do repositório poderá conectar/configurar Vercel. Vercel exige que o owner do repositório pessoal conecte ou reconecte o projeto. ([GitHub: transferência](https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository), [permissões de repo pessoal](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository), [Vercel: integração GitHub](https://vercel.com/docs/git/vercel-for-github))

Para uma pessoa mantenedora, o baseline proporcional em qualquer provedor é **PR/MR obrigatório + CI obrigatório + sem force push/deleção**, sem exigir aprovação de outra pessoa. A PR/MR vira trilha e ponto de self-review; ela não equivale a revisão independente. Não tornar o próprio admin um bypass rotineiro das verificações.

## GitHub Pro: controles e trade-offs

Com plano elegível, uma regra clássica de branch ou ruleset pode proteger `main` contra push direto, force push e deleção, exigir PR e status checks e, opcionalmente, exigir resolução de conversas. GitHub permite PR obrigatório sem exigir aprovação: o PR precisa existir; os checks selecionados precisam ter conclusão aceitável antes do merge. ([GitHub: rules disponíveis](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [branches protegidas](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches))

**Proposta solo:**

- Exigir PR para `main`, checks estáveis da CI, impedir force push e deleção.
- Não definir número mínimo de approvals: autores não podem aprovar seus próprios PRs, então um gate de “1 aprovação” torna necessário outro usuário ou bypass. ([GitHub: revisão de PR](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request))
- Considerar “Require conversation resolution” se comentários abertos devam ser tratados antes do merge. Isso obriga fechar/concluir threads; não cria revisão por pares.
- Escolher conscientemente a política de bypass. Regras clássicas não se aplicam a administradores por padrão; “Do not allow bypassing” inclui admins. Em rulesets, o bypass é explícito. “For pull requests only” preserva a trilha de PR, mas o ator autorizado ainda pode ignorar as outras regras ao fazer merge; isso pode furar o CI obrigatório. Reservar exceção apenas para emergência e registrar a razão. ([GitHub: branch protection e bypass](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [GitHub: bypass de rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository))

**Benefício:** preserva GitHub Issues/PRs/Actions, histórico e remote da Vercel; menor superfície de regressão.  
**Custo:** plano pago para habilitar proteção em privado; não resolvido se o usuário aceita esse custo. GitHub Pro documenta 3.000 Actions minutes/mês em repositório privado, contra 2.000 no Free; Actions em self-hosted runners não consomem essa franquia. A página de pricing consultada não expôs um valor pessoal atual de GitHub Pro; não inferi o preço de outras ofertas/planos. ([planos GitHub](https://docs.github.com/en/get-started/learning-about-github/githubs-plans), [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions), [pricing page](https://github.com/pricing))

## Terceira rota: transferir o repositório para a conta pessoal Pro do irmão

**Para proteção de `main`, a rota pode funcionar:** GitHub Pro inclui protected branches em repositórios privados, e GitHub alerta que transferir um repo privado para um dono Free remove essa capacidade. Se o destino mantiver Pro ativo, essa restrição de plano deixa de ser o bloqueio; a transferência, porém, **não cria a regra**. Como a `main` hoje aparece `protected=false`, o novo dono ainda precisaria configurar a proteção. ([planos GitHub](https://docs.github.com/en/get-started/learning-about-github/githubs-plans), [transferência de repositório](https://docs.github.com/en/enterprise-cloud@latest/repositories/creating-and-managing-repositories/transferring-a-repository))

**O usuário não perde o fluxo de PR, mas deixa de administrar o repo:** GitHub diz que, em transferência entre duas contas pessoais, o dono anterior passa automaticamente a colaborador; commits, issues, PRs, wiki, stars/watchers, webhooks, secrets, deploy keys e histórico Git são mantidos. Um colaborador de repo pessoal privado tem write: pode pushar branch, abrir/mesclar PR, revisar e gerir issues; apenas o proprietário tem o controle completo e ações de dono, como gerenciar webhooks e as configurações do repositório. Portanto, o irmão passa a ser o único owner capaz de manter plano, regra de branch, acesso e webhook. ([transferência de repo](https://docs.github.com/en/enterprise-cloud@latest/repositories/creating-and-managing-repositories/transferring-a-repository), [permissões em repo pessoal](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository))

**A Vercel não é bloqueio atual:** o usuário confirmou que o projeto não está publicado/conectado nela e que a infraestrutura poderá ser configurada após a fundação. Quando chegar essa etapa, o owner da conta GitHub que possui o repositório pessoal precisará conectar o repo à Vercel; isso é um requisito de setup futuro, não uma migração de produção. Se o projeto for ligado a uma Vercel Hobby pessoal, verificar que commits de outra pessoa podem exigir configuração/colaboração adicional; não há deployment atual em risco. ([Vercel: conexão com GitHub pessoal](https://vercel.com/docs/git/vercel-for-github), [Vercel: colaboração em repo privado](https://vercel.com/docs/deployments/troubleshoot-project-collaboration))

**Leitura:** transferência para Pro resolve a elegibilidade de branch protection sem trocar de provedor Git nem portar Actions. O trade-off central passa a ser ownership/administração: o irmão mantém o plano, configura a proteção e controla as configurações de owner-level; o usuário continua colaborador com write, pode trabalhar por branch/PR e mergear se a regra permitir. Como não há Vercel ativa, o owner pode configurar a integração de deploy mais tarde. Não há alteração/teste de contas neste trabalho.

## GitLab Free + Vercel: controles e trade-offs

GitLab documenta branch rules no Free. Para `main`, configure explicitamente **Allowed to merge = Maintainers** e **Allowed to push and merge = No one**; a ausência de configuração em “Allowed to push” não é equivalente a bloquear pushes. Deixe force push desabilitado. ([GitLab: protected branches](https://docs.gitlab.com/user/project/repository/branches/protected/))

Em GitLab Free, approvals podem ser registrados, mas são opcionais; regras que exigem um número de approvals estão em Premium/Ultimate. A configuração “Pipelines must succeed” exige um pipeline bem-sucedido antes do merge e está disponível no nível de projeto. Portanto, uma pessoa mantenedora pode abrir e mesclar seu próprio MR depois do pipeline, sem inventar um segundo aprovador. Configure pipeline para cada evento de merge request (`CI_PIPELINE_SOURCE == "merge_request_event"`) e evite pipeline duplicado/ambíguo; a própria documentação alerta que a prioridade entre pipelines pode alterar qual resultado decide o merge. ([GitLab: approvals e planos](https://docs.gitlab.com/user/project/merge_requests/approvals/), [MR pipelines](https://docs.gitlab.com/ci/pipelines/merge_request_pipelines/), [Pipelines must succeed](https://docs.gitlab.com/user/project/merge_requests/auto_merge/))

Vercel oferece integração direta com GitLab Free: deploy automático por push, produção na branch escolhida e Preview URL em cada MR. Também é possível fazer build no GitLab CI com `vercel build` e publicar com `vercel deploy --prebuilt`. ([Vercel: Deploying GitLab Projects](https://vercel.com/docs/git/vercel-for-gitlab), [Vercel: GitLab CI/CD](https://vercel.com/kb/guide/how-can-i-use-gitlab-pipelines-with-vercel))

Restrições que mudam a viabilidade:

- GitLab.com Free inclui **400 compute minutes/mês** para shared/instance runners; runners próprios não usam essa quota. O volume real dos builds/testes do Polaris não foi medido. ([GitLab: compute minutes](https://docs.gitlab.com/ci/pipelines/compute_minutes/))
- A página de pricing lista GitLab Free como **US$0** e confirma 400 minutos; exige cartão verificado para uso dos shared runners em determinadas contas. É possível usar runner próprio em qualquer plano, mas isso transfere manutenção do executor para o projeto. ([GitLab pricing](https://about.gitlab.com/pricing/), [compute minutes](https://docs.gitlab.com/ci/pipelines/compute_minutes/))
- Vercel não permite deploy de repositórios privados em GitLab groups sob um time Hobby; private group repos precisam de Vercel Pro. A doc ressalva exceções para repos pessoais. Confirmar o namespace do repo e o plano Vercel antes de tratar GitLab Free como rota sem custo. ([Vercel: deploy de repositórios Git](https://vercel.com/docs/git))
- O gate `Pipelines must succeed` verifica pipeline do GitLab. Se também se quiser bloquear merge até a Vercel Preview estar pronta, a forma mais clara é executar/deployar via GitLab CI ou provar que a integração reporta um status que esse gate consome. GitLab chama “external status checks” de recurso Ultimate, então não presumir esse mecanismo no Free. ([GitLab: branch rules](https://docs.gitlab.com/user/project/repository/branches/branch_rules/), [GitLab: Vercel integration](https://vercel.com/docs/git/vercel-for-gitlab))
- Migrar de GitHub para GitLab requer conferir importação de issues/MRs/configuração e reconstruir GitHub Actions em `.gitlab-ci.yml`; exports do GitLab não preservam tudo, e GitLab informa que logs/artifacts não entram em alguns caminhos de migração. Isso é esforço único, mas adiciona um vetor de falha antes de ganhar a proteção. ([GitLab: import from GitHub](https://docs.gitlab.com/user/project/import/github/), [GitLab export/import limitações](https://docs.gitlab.com/user/project/settings/import_export/))

## O que migraria e o que teria de ser refeito

| Área GitHub atual | GitLab Free / efeito provável | Evidência e ressalva |
|---|---|---|
| Git repository: commits, branches, tags | GitLab importer traz o repositório e branches. | A importação preserva o histórico Git; verificar refs, LFS e branch `main` depois do import. ([GitLab GitHub importer](https://docs.gitlab.com/user/project/import/github/)) |
| Issues, PRs, comentários e reviews | Issues/PRs viram Issues/MRs; importer lista labels, milestones, reviews, comentários/respostas e eventos entre os itens importáveis. | Muitos dados ficam com badge “Imported”. Atribuição pode falhar por mapeamento de usuários; referências `#` de GitHub não convertem perfeitamente para a convenção GitLab `!`; approvals importadas podem não virar estado de approval em alguns caminhos; attachments antigos podem falhar. ([detalhes e limitações do importer](https://docs.gitlab.com/user/project/import/github/)) |
| Branch protection / repository rules | Algumas proteções clássicas têm mapeamento para branch rules ou settings GitLab. | O importer documenta que `Require status checks to pass` **não é importado**; GitHub rulesets não aparecem como configuração migrada na lista do importer. Recriar `main` manualmente e testar o gate é necessário. ([mapeamento GitHub→GitLab](https://docs.gitlab.com/user/project/import/github/)) |
| GitHub Actions | Os arquivos `.github/workflows` são parte do repositório, mas os jobs não passam a executar no GitLab. | GitLab orienta criar `.gitlab-ci.yml` e converter workflows/jobs; configurar de novo runners, CI/CD variables/secrets, caches, artefatos e regras de pipeline. Não encontrei documentação oficial que migre o histórico de runs/Actions artifacts/secrets. ([GitLab: migrate from GitHub Actions](https://docs.gitlab.com/ci/migration/github_actions/), [project importer](https://docs.gitlab.com/user/project/import/github/)) |
| Dependabot | `.github/dependabot.yml` pode permanecer como arquivo, mas Dependabot não executa no GitLab. | GitHub diz que version updates estão disponíveis para todos os repositórios. GitLab documenta seu Dependency Scanning como Ultimate, não Free. Em Free, substituir esse comportamento requer outra automação de dependências ou aceitar perder essa verificação/PR bot. ([GitHub: Dependabot version updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-version-updates), [GitLab Dependency Scanning tiers](https://docs.gitlab.com/user/application_security/dependency_scanning/)) |
| Vercel | Integração GitLab mantém Vercel deployments, previews e produção no branch configurado. | Reautorizar/reconectar o repo e validar branch de produção, env vars e comentários de MR. Para Vercel Hobby, repo privado em GitLab group não pode deployar; GitLab Free como fornecedor Git não contorna esse limite. ([Vercel GitLab integration](https://vercel.com/docs/git/vercel-for-gitlab), [private repo plan behavior](https://vercel.com/docs/git)) |

### Custo de execução comparado

No GitHub Pro, a documentação lista 3.000 minutos Actions/mês; no GitLab Free, 400 compute minutes/mês em shared runners. Uma suite com build Next, testes, Postgres e Playwright pode tornar a cota GitLab Free relevante, mas o consumo de Polaris ainda não foi observado. Runners próprios removem a quota em ambas as ofertas e adicionam custo operacional; GitLab indica cartão verificado para shared runners em algumas contas Free. ([GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions), [GitLab compute minutes](https://docs.gitlab.com/ci/pipelines/compute_minutes/), [GitLab pricing FAQ](https://about.gitlab.com/pricing/))

## Comparação para Polaris

### Footprint atual do Polaris

- O remote atual é um repositório GitHub privado. A API de branches retorna `protected: false` para `main`; uma consulta à API de configuração confirma que o plano atual não habilita branch protection privada.
- O inventário local de `.github/` contém um workflow `ci.yml` e um hook Codex de Ultracite. Não encontrei configuração versionada de Dependabot, CodeQL, Dependency Review, CODEOWNERS, templates de PR/issues ou GitLab CI. Portanto, essas capacidades do GitHub são possibilidades futuras, não automações atuais que seriam perdidas.
- O workflow tem quatro jobs de CI em eventos de PR/push (`verify`, `e2e`, `postgres-behavior`, `admin-e2e`) e seis jobs operacionais manuais. Dois verificadores locais e a documentação de operações leem ou descrevem o workflow GitHub; migrar exigiria adaptá-los e mover secrets/variables, além de portar o CI.
- A listagem remota atual retorna uma PR merged e nenhuma issue. O volume histórico a transferir é pequeno, embora comentários/reviews daquela PR devam ser preservados se forem relevantes. Commits/branches podem ser importados; ambientes, secrets, checks, logs/artifacts do Actions e regras não acompanham o Git automaticamente.
- Vercel tem configurações separadas para `apps/web` e `apps/admin`; reconectar a origem GitLab exigiria validar ambos os projetos e os seus root directories. Não li valores de `.env` nem configurações secretas remotas.

| Caminho | Controles solo disponíveis | Esforço relativo | Principal limite |
|---|---|---|---|
| GitHub Pro privado | PR obrigatório, checks, conversas opcionais, admin incluído na regra, bypass configurável | **Baixo**; preserva repo, Actions, Dependabot e a conexão Vercel | Custo do plano não apurado nesta pesquisa; 3.000 Actions minutes/mês |
| Transferir para GitHub Pro do irmão | Mesmas regras privadas do GitHub Pro; autor atual passa automaticamente a colaborador e pode trabalhar por PR | **Baixo** para código e histórico; precisa configurar a regra | Irmão é owner/billing/admin e deve manter o Pro. Vercel ainda será conectada depois pelo owner do repo |
| GitLab Free + Vercel | MR obrigatório por branch permission, pipeline obrigatório, threads; sem approvals required no Free | **Médio/alto**; importar repo/Issues/MRs e portar workflows/configuração | 400 runner-minutes no Free; Dependabot não substitui automaticamente; Vercel Pro pode ser necessário para GitLab group privado |

O usuário aprovou transferir o repo ao irmão, que manterá a conta Pro e o papel owner/admin; o usuário seguirá como colaborador com write. É o menor delta técnico entre as rotas estudadas. A transferência e a configuração de regras ainda não foram executadas. A ausência de Vercel atual elimina risco de cutover; o owner poderá conectar Vercel depois da fundação. Nenhuma rota exige review approval de outra pessoa para operar em solo.

**Sinal de praticante, anedótico:** em uma discussão de dezembro de 2025, alguém que relata migrar uma organização de cerca de 40 pessoas de GitHub para GitLab self-managed diz que Actions não foi uma conversão de “find and replace”, branch protections/webhooks precisaram ser refeitos e a migração completa levou cerca de 2,5 meses. Isso não estima o esforço de um repo solo no GitLab.com Free; apenas coincide com a lista oficial de configurações/jobs a portar. ([relato em r/devops](https://www.reddit.com/r/devops/comments/1ph3dca/looking_to_migrate_company_off_github_whats_the/))

## Alinhamento proporcional de `main`

1. **Obrigatório:** mudanças chegam por PR/MR; build, typecheck e os checks de CI escolhidos passam; force push e deleção proibidos.
2. **Self-review:** usar checklist/descrição e examinar diff antes do merge. Self-review não deve ser registrada como aprovação independente.
3. **Conversas:** começar sem bloqueio se quase não houver comentários; ativar resolução obrigatória quando threads forem usadas para revisão e o autor puder resolvê-las.
4. **Approvals:** manter sem mínimo por enquanto. Se existir segundo revisor ou surgir exigência de segregação de funções, reavaliar uma approval independente.
5. **Bypass:** sem bypass normal de admin. Se surgir urgência, preferir mudança temporária e rastreável da regra; bypass de PR pode deixar o registro, mas ignorar o check.

## Decisões em aberto para a conversa

- A transferência será aceita e executada pelo irmão? A decisão foi aprovada para o plano, mas não foi feita nesta revisão.
- Os checks de CI só devem ser exigidos depois de restaurar o baseline verde e confirmar nomes/contextos publicados pela execução dos PRs.
- A resolução obrigatória de conversas fica opcional inicialmente. Reavaliar se PRs passarem a usar threads de revisão com frequência.
- Sem bypass administrativo rotineiro; qualquer exceção futura deve ser excepcional, rastreável e reavaliada quando a regra for configurada.

**Limitação:** as docs comprovam disponibilidade de features e integrações, não a duração real da migração, uso de minutos, planos das contas ou a configuração de Vercel futura. Não consultei configurações de conta do irmão, não fiz mutações e não testei transferência.
